= CLI Reference
:description: Full reference for the zed-http command-line interface — all subcommands, flags, exit codes, and examples.

The `zed-http` binary is the out-of-process CLI companion to the Zed extension.
It is built from the `zed-http-cli` crate in `crates/zed-http-cli/`.
All request execution, parsing, validation, formatting, introspection, and import work is handled by this binary; the Zed extension only provides language support and task wiring.

The CLI can be used independently of Zed — for example in CI pipelines or shell scripts — by invoking `zed-http` directly.

[source,bash]
----
zed-http --help
zed-http <subcommand> --help
----

== Subcommands

* xref:#run[run] — execute a single HTTP or GraphQL request
* xref:#run-all[run-all] — execute every request in a file with a pass/fail summary
* xref:#check[check] — validate every request in a file without sending
* xref:#list[list] — print a numbered request listing
* xref:#envs[envs] — list available environment names
* xref:#format[format] — re-emit a file in canonical layout
* xref:#introspect[introspect] — run a GraphQL introspection query and cache the schema
* xref:#schema[schema] — inspect cached schemas
* xref:#import[import] — translate a Postman v2.1 collection, a curl command, or a HAR archive into a `.http` file
* xref:#completions[completions] — emit a shell completion script for bash, zsh, fish, powershell, or elvish

== Exit codes

All subcommands use the following shared exit code scheme:

[cols="1,4", options="header"]
|===
|Code |Meaning

|`0`
|Success.

|`1`
|Generic error — network or TLS failure, a file that cannot be read or parsed, a malformed `--var` argument, `format --check` finding a non-canonical file, etc.

|`2`
|Test failure — one or more `# @expect-*` response assertions failed (`run`), or one or more requests in a `run-all` invocation failed (HTTP status ≥ 400, a failed assertion, or a request that errored).

|`3`
|Validation failure — pre-flight validation rejected the request file before anything was sent (`run`, `run-all`, and `check`).
|===

[[run]]
== zed-http run

=== Synopsis

[source,bash]
----
zed-http run --file <path>
             [--line <n> | --name <name>]
             [--column <n>]
             [--env <name>]
             [--worktree <path>]
             [--output pretty|json|raw]
             [--verbose]
             [--no-validate]
             [--no-cookies]
             [--cookie-jar <path>]
             [--var <NAME=VALUE>]...
----

=== Description

Executes a single request selected from the given `.http` or `.rest` file.
The request is selected by line number, by name, or — when neither is specified — the first request in the file.
Unless `--no-validate` is passed, the selected request is validated (including schema-aware checks for GRAPHQL requests when a cached schema is available) before the HTTP connection is opened.
After execution the response body is saved to `<base>/.zed-http/responses/` relative to the `.http` file.
Assertion directives (`# @expect-*`) are evaluated against the live response and cause a non-zero exit on failure.

Built-in dynamic variables (`{{$uuid}}`, `{{$timestamp}}`, `{{$isoTimestamp}}`, `{{$randomInt}}`) are resolved automatically — no declaration needed.
They are generated once per `run` invocation so all references within the same request expand to the same value.
See xref:directives.adoc#dynamic-variables[Dynamic variables] for the full semantics.

See xref:assertions.adoc[Response assertions] and xref:cookies.adoc[Persistent cookies] for related features.

=== Flags

[cols="2,1,4", options="header"]
|===
|Flag |Type / default |Description

|`--file <path>`
|path, *required*
|The `.http` or `.rest` file to read.

|`--line <n>`
|integer, optional
|Select the request whose block contains line `n` (1-based). Conflicts with `--name`.

|`--name <name>`
|string, optional
|Select the request with this name (case-insensitive). Conflicts with `--line`.

|`--column <n>`
|integer, optional
|Reserved for future use. Accepted but not currently used in request selection.

|`--env <name>`
|string, optional
|Load the named environment from `http-client.env.json` (and `http-client.private.env.json`). Overrides any `# @env` directive in the file.

|`--worktree <path>`
|path, optional
|Root path for environment file discovery and `.zed-http/` artifact directories. Defaults to the directory containing `--file`.

|`--output <mode>`
|`pretty` \| `json` \| `raw`, default `pretty`
|Output format. `pretty` — human-readable status, duration, content-type, saved path, and preview. `json` — structured envelope (see xref:#json-output-envelope[JSON output envelope]). `raw` — response body verbatim.

|`--verbose`
|flag
|Before sending, print the resolved method, URL, headers, variables (secrets masked), and body.

|`--no-validate`
|flag
|Skip pre-flight validation. Use for ad-hoc debugging when a request is intentionally malformed.

|`--no-cookies`
|flag
|Disable the persistent cookie jar for this invocation. Cookies are neither read nor written.

|`--cookie-jar <path>`
|path, optional
|Override the cookie jar file location. Defaults to `<base>/.zed-http/cookies.json`.

|`--var <NAME=VALUE>`
|string, repeatable
|Override a variable for this invocation. Wins over every other layer (env files, in-file `@vars`, dynamic vars). Repeatable — `--var host=https://staging.example.com --var token=abc`. When the same name is given more than once, the last occurrence wins. See xref:environments.adoc#variable-resolution-layers[Variable resolution layers].
|===

[[json-output-envelope]]
The JSON envelope emitted by `--output json` has the following shape:

[source,json]
----
{
  "request": {
    "name": "List users",
    "method": "GET",
    "url": "https://api.example.com/users",
    "line": 4
  },
  "response": {
    "status": "200 OK",
    "duration_ms": 87,
    "content_type": "application/json",
    "saved_path": ".zed-http/responses/2026-05-20T14-32-10-list-users.json",
    "redirect_path": null,
    "body": { ... },
    "assertion_failures": [],
    "captured": {},
    "capture_warnings": []
  }
}
----

`response.assertion_failures` is a non-empty array when any `# @expect-*` directive is violated.
Each entry has `line` (source line in the `.http` file) and `message` fields.

`response.captured` is a map of variable name to captured value (masked with `***` for sensitive keys — see xref:captures.adoc#secret-masking[Secret masking]).
`response.capture_warnings` is an array of `{variable, line, message}` objects for any captures that could not be resolved.
See xref:captures.adoc[] for the full reference.

=== Exit codes

[cols="1,4", options="header"]
|===
|Code |Condition

|`3`
|Pre-flight validation failed (unless `--no-validate`).

|`1`
|The HTTP request itself failed (network error, TLS error).

|`2`
|One or more `# @expect-*` assertions were not satisfied.

|`0`
|The request completed and all assertions passed.
|===

=== Example

[source,bash]
----
zed-http run --file api/users.http --line 12 --env dev --output json
----

[[run-all]]
== zed-http run-all

=== Synopsis

[source,bash]
----
zed-http run-all --file <path>
                 [--env <name>]
                 [--worktree <path>]
                 [--output pretty|json|raw]
                 [--bail]
                 [--no-validate]
                 [--no-cookies]
                 [--cookie-jar <path>]
                 [--var <NAME=VALUE>]...
----

=== Description

Executes every request in the given `.http` or `.rest` file in declaration order.
This is the primary command for smoke-test suites and CI pipelines where you want to run a whole file and get a pass/fail result for each request.

Unless `--no-validate` is passed, the entire file is validated (including schema-aware GRAPHQL checks) before any request is sent.
A single cookie jar is built at the start and shared across all requests in the run, so login → action flows work without any extra setup.
The jar is persisted once at the end of the run.

Dynamic variables (`{{$uuid}}`, `{{$timestamp}}`, etc.) are resolved independently for each request, so each iteration gets a fresh set.
See xref:directives.adoc#dynamic-variables[Dynamic variables] for details.

==== Pretty output

In `pretty` mode (the default), the filename is printed first, then one status line per request:

----
smoke-tests.http
  ✓ Health check                  200 OK                   42ms
  ✓ Create order                  201 Created             108ms
  ✗ Verify order status           200 OK                   55ms
      smoke-tests.http:31: expected status [404], got 200

3 requests: 2 passed, 1 failed
----

Each assertion failure appears on a fresh line indented below the request that failed, in `<file>:<line>: <message>` format.
The summary line at the end counts total, passed, failed, and (when `--bail` was triggered) skipped requests.

==== JSON output

In `json` mode the command emits a single JSON object:

[source,json]
----
{
  "file": "smoke-tests.http",
  "summary": {
    "total": 3,
    "passed": 2,
    "failed": 1,
    "skipped": 0,
    "bailed_at": null
  },
  "requests": [
    {
      "index": 1,
      "name": "Health check",
      "line": 4,
      "method": "GET",
      "url": "https://staging.example.com/health",
      "ok": true,
      "status_code": 200,
      "status": "200 OK",
      "duration_ms": 42,
      "error": null,
      "assertion_failures": [],
      "captured": {},
      "capture_warnings": []
    }
  ]
}
----

`summary.bailed_at` is a 1-based request index when `--bail` triggered early termination, otherwise `null`.
`requests[].assertion_failures` follows the same `{line, message}` shape as the `run` JSON envelope.
`requests[].captured` is a map of variable name to captured value; sensitive keys are masked with `***`.
`requests[].capture_warnings` is an array of `{variable, line, message}` objects for any captures that did not resolve.
See xref:captures.adoc[] for the full reference.

==== Raw output

In `raw` mode, one tab-separated row is printed per request:

----
PASS\t<status>\t<name>\t<url>
FAIL\t<status>\t<name>\t<url>
----

Useful for post-processing with `awk`, `grep`, or a CI log parser.

=== Flags

[cols="2,1,4", options="header"]
|===
|Flag |Type / default |Description

|`--file <path>`
|path, *required*
|The `.http` or `.rest` file to run.

|`--env <name>`
|string, optional
|Load the named environment from `http-client.env.json` (and `http-client.private.env.json`). Overrides any `# @env` directive in the file.

|`--worktree <path>`
|path, optional
|Root path for environment file discovery and `.zed-http/` artifact directories.

|`--output <mode>`
|`pretty` \| `json` \| `raw`, default `pretty`
|Output format. See above for the shape of each mode.

|`--bail`
|flag
|Stop execution at the first failed request.
  The remaining requests are counted as skipped and appear in the summary.
  The exit code is still non-zero.

|`--no-validate`
|flag
|Skip the whole-file pre-flight validation step.
  Useful when iterating on a file that is not yet well-formed.

|`--no-cookies`
|flag
|Disable the shared cookie jar for this run. Cookies are neither read nor written.

|`--cookie-jar <path>`
|path, optional
|Override the cookie jar file location. Defaults to `<base>/.zed-http/cookies.json`.
  The jar is loaded once at the start of the run, shared across all requests, and persisted once at the end.
  This is what makes a login request at position 1 supply credentials to action requests at positions 2, 3, etc.

|`--var <NAME=VALUE>`
|string, repeatable
|Seed the variable map before request 1 runs. Repeatable. `# @capture` results from each response are merged on top of this seed as the run progresses, so later requests can reference both the initial seeds and the captured values.
  When the same name is given more than once, the last `--var` occurrence wins.
  See xref:captures.adoc#composing-with-var[Composing with `--var`] and xref:environments.adoc#variable-resolution-layers[Variable resolution layers].
|===

=== Exit codes

[cols="1,4", options="header"]
|===
|Code |Condition

|`3`
|Pre-flight validation failed (unless `--no-validate`).

|`2`
|Any request in the file failed (HTTP status ≥ 400, a failed assertion, or a request that errored), or `--bail` was triggered.

|`0`
|Every request passed.
|===

=== Example

[source,bash]
----
zed-http run-all --file smoke-tests.http --env staging --bail
----

Expected pretty output when the third request fails a `# @expect-status` assertion:

----
smoke-tests.http
  ✓ Health check                  200 OK                   38ms
  ✓ Create order                  201 Created              92ms
  ✗ Verify order status           200 OK                   51ms
      smoke-tests.http:31: expected status [404], got 200

3 requests: 2 passed, 1 failed
bailed at request #3
----

[[check]]
== zed-http check

=== Synopsis

[source,bash]
----
zed-http check --file <path>
               [--env <name>]
               [--worktree <path>]
----

=== Description

Parses every request block in the file and reports validation issues without making any HTTP connections.
Issues are printed to stderr in `<file>:<line>: [<request-name>] <message>` format.
When a cached schema is available for a GRAPHQL request's URL (after a prior `introspect` run), schema-aware field validation is also applied.
Exits non-zero if any issue is found.

Use this command in CI to gate on well-formed request files before executing them.
See xref:directives.adoc[Directives reference] for a description of what the validator checks.

=== Flags

[cols="2,1,4", options="header"]
|===
|Flag |Type / default |Description

|`--file <path>`
|path, *required*
|The `.http` or `.rest` file to validate.

|`--env <name>`
|string, optional
|Environment to use when resolving `{{variable}}` references in URLs for schema lookup. Requests with unresolved variables skip schema validation rather than reporting false positives.

|`--worktree <path>`
|path, optional
|Root path for environment file and schema cache discovery.
|===

=== Exit codes

[cols="1,4", options="header"]
|===
|Code |Condition

|`3`
|At least one validation issue was found.

|`0`
|All requests passed; a summary is printed.
|===

=== Example

[source,bash]
----
zed-http check --file api/users.http --env dev --worktree .
----

[[envs]]
== zed-http envs

=== Synopsis

[source,bash]
----
zed-http envs --file <path>
              [--worktree <path>]
----

=== Description

Lists every environment name defined across `http-client.env.json` and `http-client.private.env.json`, printing one name per line.
Duplicate names (present in both files) appear only once.
The search walks up from the directory containing `--file` to `--worktree`, using the same discovery rules as `run`.
See xref:environments.adoc[Environments and variables] for the full lookup algorithm.

=== Flags

[cols="2,1,4", options="header"]
|===
|Flag |Type / default |Description

|`--file <path>`
|path, *required*
|The `.http` or `.rest` file whose directory tree is searched for environment files.

|`--worktree <path>`
|path, optional
|Upper bound for the directory walk. Defaults to the directory containing `--file`.
|===

=== Example

[source,bash]
----
zed-http envs --file api/users.http --worktree .
----

[[format]]
== zed-http format

=== Synopsis

[source,bash]
----
zed-http format --file <path>
                [--in-place | --check]
----

=== Description

Re-emits a request file in canonical layout: trimmed whitespace, a single space after the method keyword, `Header: value` on its own line, a blank line before the body, option directives before the request line, and response redirect after the body.
Without any mode flag the formatted output is printed to stdout.

WARNING: `zed-http format` discards non-directive comments (`# free text`) that appear inside request blocks.
Commentary outside request blocks is also dropped.
Directive comments (`# @timeout`, `# @expect-status`, etc.) are preserved.
See xref:roadmap.adoc#known-limitations[Known limitations].

=== Flags

[cols="2,1,4", options="header"]
|===
|Flag |Type / default |Description

|`--file <path>`
|path, *required*
|The `.http` or `.rest` file to format.

|`--in-place`
|flag
|Overwrite the source file with the formatted output. Conflicts with `--check`.

|`--check`
|flag
|Exit non-zero if the file is not already in canonical form, without writing anything. Useful in CI. Conflicts with `--in-place`.
|===

=== Exit codes

With `--check`: exits `1` when the file is not in canonical form, `0` when it already is.

=== Example

[source,bash]
----
# Check in CI
zed-http format --file api/users.http --check

# Normalise in place
zed-http format --file api/users.http --in-place
----

[[introspect]]
== zed-http introspect

=== Synopsis

[source,bash]
----
zed-http introspect --file <path>
                    [--line <n> | --name <name>]
                    [--env <name>]
                    [--worktree <path>]
                    [--output <path>]
----

=== Description

Sends a standard GraphQL introspection query against the URL resolved from the selected `GRAPHQL` request block.
The `--env` / `--worktree` flags are honoured so that bearer tokens and host variables resolve correctly.
The `data` portion of the introspection response is saved as a JSON schema file.
By default the file is written to `<base>/.zed-http/schema/<host>.json` where `<host>` is derived from the request URL; use `--output` to choose a custom path.
Once a schema is cached, xref:#check[check] and xref:#run[run] use it for schema-aware GRAPHQL field validation.
See xref:graphql.adoc#introspection[Schema introspection] for a walkthrough.

The selected request *must* use the `GRAPHQL` pseudo-method; `introspect` exits with an error if an HTTP method request is selected.

=== Flags

[cols="2,1,4", options="header"]
|===
|Flag |Type / default |Description

|`--file <path>`
|path, *required*
|The `.http` or `.rest` file containing the GRAPHQL request.

|`--line <n>`
|integer, optional
|Select by line number. Conflicts with `--name`.

|`--name <name>`
|string, optional
|Select by request name. Conflicts with `--line`.

|`--env <name>`
|string, optional
|Environment for variable resolution (e.g. bearer token, host URL).

|`--worktree <path>`
|path, optional
|Root path for environment file and schema cache directory.

|`--output <path>`
|path, optional
|Custom path for the cached schema file. Overrides the default `<base>/.zed-http/schema/<host>.json` location.
|===

=== Exit codes

Non-zero when the selected request is not a GRAPHQL request, when the introspection HTTP request fails, or when the server returns GraphQL errors in the response body.

=== Example

[source,bash]
----
zed-http introspect --file api/graphql.http --name "GetUser schema" --env dev
----

[[import]]
== zed-http import postman

=== Synopsis

[source,bash]
----
zed-http import postman --file <collection.json>
                        [--out <path>]
----

=== Description

Translates a Postman v2.1 collection export into a canonical `.http` file.
Nested folders are flattened with a `parent / child` naming convention in the request names.
`GET`, `POST`, `PUT`, `PATCH`, `DELETE`, and similar methods are mapped directly.
`raw` JSON bodies become standard JSON request bodies.
`graphql` body mode becomes a `GRAPHQL` pseudo-method request.
Collection-level variables become `@var = value` in-file declarations.
Multipart/form-data bodies are skipped (logged to stderr).

Without `--out` the result is printed to stdout so you can preview it before writing.
See xref:postman-import.adoc[Postman collection import] for a step-by-step guide.

=== Flags

[cols="2,1,4", options="header"]
|===
|Flag |Type / default |Description

|`--file <path>`
|path, *required*
|The Postman v2.1 collection JSON file to import.

|`--out <path>`
|path, optional
|Write the translated `.http` file to this path (parent directories are created). Defaults to stdout.
|===

=== Exit codes

Non-zero when the collection file cannot be read or is not a valid Postman v2.1 JSON document.

=== Example

[source,bash]
----
zed-http import postman --file exports/my-api.postman_collection.json \
                        --out api/my-api.http
----

[[import-har]]
=== zed-http import har

==== Synopsis

[source,bash]
----
zed-http import har --file <path>
                    [--out <path>]
                    [--name-prefix "<prefix>"]
----

==== Description

Translates a HAR 1.2 archive — the JSON file produced by *Save all as HAR with content* in browser devtools — into a multi-request `.http` file.
Each entry in `log.entries[]` becomes one canonical request block.

`--file` is required; there is no inline or `--stdin` input mode in v0.4.5.
Without `--out`, the result is written to stdout.
When `--out` is given the parent directory is created automatically.

Request names default to `<index>: <METHOD> <path-and-query>` so `zed-http list` output stays scannable.
HTTP/2 pseudo-headers (`:authority`, `:method`, `:path`, `:scheme`, `:status`) are stripped automatically — they are an artefact of HTTP/2 captures and would cause errors when a request is replayed.
`postData.text` becomes an inline body when present; `postData.mimeType` is preserved via the original `Content-Type` header.
Multipart bodies (`postData.params`) are recognised but dropped with a `multipart body skipped` note appended to the request name.

See xref:har-import.adoc[HAR archive import] for a step-by-step guide with worked examples.

==== Flags

[cols="2,1,4", options="header"]
|===
|Flag |Type / default |Description

|`--file <path>`
|path, *required*
|The HAR 1.2 archive to import. Must be a UTF-8 JSON file; `.har.gz` is not auto-decoded.

|`--out <path>`
|path, optional
|Write the resulting `.http` content to this path (parent directories are created). Defaults to stdout.

|`--name-prefix "<prefix>"`
|string, optional
|Prepend this string to every imported request name, e.g. `--name-prefix "Smoke"` produces names like `Smoke / 1: GET /api/users`. The value is trimmed; an all-whitespace prefix is treated as no prefix.
|===

==== Exit codes

Non-zero when:

* The file cannot be read.
* The file is not valid JSON.
* The top-level `/log/entries` array is absent (not a valid HAR 1.2 document).

==== Example

[source,bash]
----
# Import to a file
zed-http import har --file session.har --out smoke/session.http

# Import with a name prefix, preview on stdout
zed-http import har --file checkout.har --name-prefix "Checkout flow"
----

[[import-curl]]
=== zed-http import curl

==== Synopsis

[source,bash]
----
zed-http import curl ['<curl command>']
                     [--file <path>]
                     [--stdin]
                     [--out <path>]
                     [--name "<name>"]
----

==== Description

Translates a `curl` command into a single canonical `.http` request block.
The primary use-case is the *Copy as cURL* action in browser devtools: paste the output (including multi-line backslash continuations) and receive a `.http` block suitable for `zed-http run` or `zed-http run-all`.

Input is accepted in exactly one of three mutually exclusive shapes — positional argument, `--file`, or `--stdin`.
Passing more than one at once is rejected by the argument parser.
When no input shape is provided the command exits with an error explaining the three options.

Without `--out` the result is written to stdout so it can be previewed or redirected.
When `--out` is given the parent directory is created automatically and a confirmation line is printed to stderr.

Recognised flags cover the set that devtools actually emit: `-X` / `--request`, `-H` / `--header`, `-d` / `--data` / `--data-raw` / `--data-binary` / `--data-ascii`, `--data-urlencode`, `-u` / `--user`, `-A` / `--user-agent`, `-e` / `--referer`, `-b` / `--cookie`, `-G` / `--get`, and the bare URL.
Cosmetic flags (`--compressed`, `-L`, `-s`, `-k`, `-v`, `--http2`, etc.) are silently consumed.
Multipart (`-F` / `--form`) is recognised but the body is dropped with a `TODO` note in the request name.

See xref:curl-import.adoc[curl command import] for a full walkthrough with worked examples.

==== Flags

[cols="2,1,4", options="header"]
|===
|Flag |Type / default |Description

|`[CURL_COMMAND]`
|string, optional
|The curl command as a positional argument (quoted).
 Conflicts with `--file` and `--stdin`.

|`--file <path>`
|path, optional
|Read the curl command from a file.
 Conflicts with the positional argument and `--stdin`.

|`--stdin`
|flag
|Read the curl command from stdin.
 Conflicts with the positional argument and `--file`.

|`--out <path>`
|path, optional
|Write the resulting `.http` content to this path (parent directories are created).
 Defaults to stdout.

|`--name "<name>"`
|string, optional
|Override the imported request name.
 Defaults to `Imported from curl`.
|===

==== Exit codes

Non-zero when:

* No input shape is provided.
* Two conflicting input shapes are provided simultaneously.
* The curl command contains an unterminated quoted string.
* An explicit `-X` value is not a recognised HTTP method.
* No URL can be found in the curl command.

==== Example

[source,bash]
----
# Inline positional argument
zed-http import curl 'curl https://api.example.com/health' \
  --name "Health check" \
  --out api/health.http

# From clipboard on macOS, written to stdout
pbpaste | zed-http import curl --stdin

# From a saved file
zed-http import curl --file paste.txt --out api/orders.http
----

Multi-line devtools paste (backslash continuations are handled transparently):

[source,bash]
----
zed-http import curl \
  'curl "https://api.example.com/api/orders" \
    -H "accept: application/json" \
    -H "content-type: application/json" \
    --data-raw "{\"item\":\"widget\",\"qty\":3}"'
----

Expected output:

[source,asciidoc]
----
### Imported from curl
POST https://api.example.com/api/orders
accept: application/json
content-type: application/json

{"item":"widget","qty":3}
----

[[completions]]
== zed-http completions

=== Synopsis

[source,bash]
----
zed-http completions {bash|zsh|fish|powershell|elvish}
----

=== Description

Emits a clap-generated shell completion script for the chosen shell to stdout.
Redirect the output to your shell's completion directory once; subsequent tab completions will offer all `zed-http` subcommand names, flag names, and value enum variants (such as `pretty`, `json`, `raw` for `--output`).

Because the script is generated from the same clap definition that drives the binary, it stays in sync with the CLI surface automatically — re-run the command after upgrading to capture any new subcommands or flags.

This is a one-shot generator, not a persistent shell hook.
You run it once per install (or once per upgrade) and redirect the output to a file; the shell sources that file on startup.

=== Arguments

[cols="2,1,4", options="header"]
|===
|Argument |Values |Description

|`<SHELL>`
|`bash` \| `zsh` \| `fish` \| `powershell` \| `elvish`
|The target shell. The generated script format differs per shell; passing the wrong shell name will produce a script that cannot be sourced by your actual shell.
|===

=== Examples

==== Bash

[source,bash]
----
zed-http completions bash | sudo tee /etc/bash_completion.d/zed-http
----

On systems without a system-wide completions directory, or when you do not have `sudo` access, install to your home directory instead:

[source,bash]
----
mkdir -p ~/.local/share/bash-completion/completions
zed-http completions bash > ~/.local/share/bash-completion/completions/zed-http
----

==== Zsh

[source,bash]
----
zed-http completions zsh | sudo tee /usr/local/share/zsh/site-functions/_zed-http
----

Ensure the site-functions directory is on your `$fpath`.
If you use a user-local completions directory (e.g. with `oh-my-zsh` or a custom `$fpath` entry):

[source,bash]
----
zed-http completions zsh > ~/.zsh/completions/_zed-http
----

==== Fish

[source,bash]
----
zed-http completions fish > ~/.config/fish/completions/zed-http.fish
----

Fish loads completions from `~/.config/fish/completions/` automatically; no further configuration is needed.

==== PowerShell

[source,powershell]
----
zed-http completions powershell | Out-String | Invoke-Expression
----

To make completions persist across sessions, append the generated script to your PowerShell profile:

[source,powershell]
----
zed-http completions powershell >> $PROFILE
----

==== Elvish

[source,bash]
----
zed-http completions elvish > ~/.elvish/lib/zed-http.elv
----

Then add the following line to `~/.elvish/rc.elv`:

[source,elvish]
----
use zed-http
----

=== Exit codes

Always exits `0`.
The shell argument is validated by clap at parse time; an invalid value produces a usage error before the command runs.

[[editor-task-variables]]
== Editor task variables

When `zed-http` is invoked from a Zed task, the following Zed task variables are available.
The bundled `.zed/tasks.json` (and `tasks.json.example`) map these onto the corresponding CLI flags.

[cols="1,2,2", options="header"]
|===
|Variable |CLI flag it maps to |Description

|`$ZED_FILE`
|`--file`
|Absolute path to the file currently open in the active editor buffer.

|`$ZED_ROW`
|`--line`
|1-based line number of the cursor position. Used by `run` to select the request block under the cursor.

|`$ZED_COLUMN`
|`--column`
|1-based column of the cursor position. Passed through to `--column` (accepted but currently unused).

|`$ZED_WORKTREE_ROOT`
|`--worktree`
|Root path of the Zed worktree containing the open file. Used for environment file discovery and `.zed-http/` artifact placement.
|===

See xref:zed-integration.adoc[Running from Zed] for how these variables are wired into Zed tasks.
